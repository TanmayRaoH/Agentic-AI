## Section 11 findings (fastmcp 4.1.6)
| Item | Finding |
|---|---|
| Middleware hooks | `on_call_tool(context, call_next) -> ToolResult` and `on_list_tools(context, call_next) -> Sequence[Tool]` exist. Also `on_request`, `on_message`, `on_initialize`, `on_discover`, resource/prompt hooks. |
| Header access | `fastmcp.server.dependencies.get_http_headers(include_all=False, include=None)` exists. **Default strips `authorization`, `cookie`, `mcp-session-id`** etc.; `x-task-grant` is not stripped. Query-param fallback not needed unless tests show otherwise. |
| Proxy API | Differs from guide. No `fastmcp.server.proxy` module. Proxy classes live in `fastmcp.server.providers.proxy` (`FastMCPProxy`, `ProxyClient`, `StatefulProxyClient`, `ProxyProvider`). `fastmcp.server.create_proxy(target, *, mode=None, **settings)` is the factory. `FastMCP.mount(server, namespace=None, tool_names=None)` replaces prefix-style mounting (`namespace` not `prefix`). |
| Package top level | `import fastmcp` exposes only lazy attrs (`settings`, `utilities`); import `FastMCP` from `fastmcp.server.server` (verify exact path at Phase 2). |
| Sessions (verified Phase 2) | **Differs from the guide.** fastmcp 4 clients negotiate the 2026-07-28 protocol era by default; there every request is its own connection and `ctx.session_id` is a new uuid per request. Only handshake-era clients (`Client(mode="legacy")`, the official SDKs today) send a stable `mcp-session-id` header. The gateway reads that header (`get_http_headers(include={"mcp-session-id"})`, it is stripped by default) and otherwise identifies a client as `stateless:<hash(client address + user agent)>` with one WARN audit row. `max_sessions` is therefore only meaningful for handshake-era clients; grant state never depends on it. |
| Mounting (verified Phase 2) | `FastMCP.mount(create_proxy(transport), namespace=name)` gives `fs_read_file` style names. Middleware on the parent sees calls to mounted proxies. `mcp.list_tools(run_middleware=False)` lists without our middleware (used for startup discovery). |
| Headers (verified Phase 2) | `x-task-grant` arrives intact through `get_http_headers()`; query-param fallback `task_grant` is implemented but untested over HTTP. |
| Upstream failures (verified Phase 2) | A dead upstream surfaces as `ToolError("Error calling tool ...")` whose cause chain holds `MCPError: Connection closed`; middleware walks the chain to tell this (UPSTREAM_ERROR) from an ordinary tool error (passed through). |
| HTTP serving | `mcp.http_app()` served by our own `uvicorn.Server` so tests can start and stop it cleanly. `StdioTransport(keep_alive=True)` keeps one subprocess per upstream. |
| Server-initiated requests (F39) | `default_proxy_sampling_handler`, `default_proxy_elicitation_handler`, `default_proxy_roots_handler` exist in the proxy provider: the proxy **can relay sampling/elicitation to the client**. F39 must override these handlers. Verify at Phase 5. |
| Tool-name prefixing | To verify at Phase 2 by printing real `list_tools` names, then align tools.yaml. |

## Phase 1 design decisions
- Demo servers expose unprefixed tool names (`read_file`, `fetch`, `send_email`, `read`); the upstream name is the prefix, so the agent sees `fs_read_file`, `web_fetch`, `mail_send_email`, `notes_read` (matches tools.yaml). The unprotected backend adds the prefix itself, the gateway will do it via `mount(namespace=...)`.
- Added tools beyond the guide's six, all listed in tools.yaml: `fs_list_files`, `fs_run_command` (simulated, never executes), `notes_write`. Needed for the benign "list files" scenario, D03 (shell metacharacters) and E02 (stage via notes).
- The fs server is jailed to a fake world dir (`eval/runtime/world`, copied from `eval/fixtures/world` before every run). Absolute paths map into it and `..` cannot climb out, so unprotected attacks never touch the real disk. `/etc/passwd` is a fake file.
- Ground truth: `eval/runtime/logs/upstream_calls.jsonl` (every executed call), `mail_log.jsonl` and `web_requests.jsonl` (sinks), plus world files compared with the fixture.
- Rug-pull server (`demo/servers/rugpull_server.py`, env `RUGPULL_MODE`): modes poisoned, rugpull, schema, shadow. The listing counter lives in `rugpull_state.json` in the log dir, so it counts across processes. "Description changes after first listing" means: the first `tools/list` is benign, the second and later are not. When the gateway lists at startup, that startup listing counts as the first.
- Extra scenario fields beyond the guide's example: `variant` (swaps the web or fs upstream for the rug-pull server), `list: true` step (agent reloads its tool list), template ops rev, url, rot13, upper, spaced, dashed, half1, half2, slice, repeat, `${step.N.text}`.
- A04 and E03 both split the canary itself (halves / three slices), not the note text, so the split is deterministic.
- Windows detail: fs_write_file writes with `newline=""` so `\n` is not turned into `\r\n` (this broke BN06 until fixed).

## Phase 2 design decisions and interface changes
- Section 5.1 contract changes (recorded as required): `grants`, `sessions`, `audit` functions are async and take the `Store` as first argument (no global state). `sessions.touch_session` returns a bool (admitted or not). `Verdict` gained a `grant_id` field and a `code` property. `Engine.check_result` and `Engine.audit_call` gained optional latency and upstream_ms parameters. `Engine.deny` gained an optional `grant_id`.
- Pipeline implemented so far: step 1 (grant, status, sessions), step 2 (suspended), step 12 (atomic budget), step 13 (forward with per-upstream timeout), audit of call and result. Steps 3 to 11 and result scanning are marked in `engine.py`.
- `grants.py` ships the minimum (create, resolve, reserve, revoke) early because the concurrency test needs the budget. Creation limits, registry validation and `allow_critical` (T14) still belong to Phase 3.
- Monitor mode: every deny is audited as `would_deny` and forwarded, except FIREWALL_ERROR, which always blocks (fail closed). Programmatic `mode=` bypasses the FW_ALLOW_MONITOR check (used by the eval harness); the env path (`python -m firewall.server`) enforces it.
- Audit masking (`audit.mask`) currently masks every string (first 4 chars + length + hash). Phase 4 refines it to mask only detected secrets and keep harmless short values readable.
- Audit rows: one `call` row per tools/call decision, one `result` row per forwarded call (also for UPSTREAM_ERROR, UPSTREAM_TIMEOUT), `system` rows for WARNs. Event id is `ev_<audit row id>`.
- Resources and prompts: listing returns empty, read/get raise with code RESOURCES_DISABLED unless `allow_resources` (full scanning of allowed resources comes with F14).
- Eval harness: `eval/gateway_harness.py` starts the gateway in-process, reusing it across scenarios except those with a malicious-upstream `variant` (fresh gateway per run so the rug-pull listing counter starts at the gateway's startup listing). The eval client uses `mode="legacy"` so session semantics apply.
- Phase 2 review fixes: (1) request-path state changes go through `sessions.update_state`, an atomic merge under the store lock (labels add-only, counters incremented in place); `save_state` is a full overwrite for operator/test use only, because a read-modify-write could erase a concurrent label (a taint reset). (2) `sessions` primary key is now `(id, grant_id)`: stateless-era clients share one derived id, and two grants on one host must not collide. The earlier test `test_f02_session_bound_to_one_grant` encoded the opposite (wrong) rule and was replaced by `test_f02_same_session_id_on_two_grants_counts_per_grant`. (3) Session rows older than 1 hour are pruned. (4) The `task_grant` query-parameter fallback now has a test. Schema changed with no migration: delete any old `fw.db`.
- Known gaps left for later phases (by design): tools/list is not yet filtered to the grant (F03, Phase 3), so an enforce-mode client without a grant can still see the catalog until then; server-initiated sampling/elicitation is still relayed by the proxy (F39, Phase 5); no hash chain yet (F20 Tier 2, Phase 6). Prefer the `X-Task-Grant` header over the query parameter: URLs end up in access logs.
- Seed script: `uv run python -m firewall.seed_grant --tools notes_read ...` (T11).

## Phase 3 design decisions
- New modules: `registry.py` (F05), `policy.py` (F07), `admin_api.py` (F17), `cli.py` (F19). `grants.py` now enforces F06 limits (ttl <= 24 h, max_calls <= 200, max_sessions <= 5, non-empty tools, registry membership, `allow_critical`).
- Pipeline now runs: 1 grant, 2 suspended, 3 unknown tool (not in tools.yaml, or no upstream provides it), 5 grant scope, 10 policy rules, 11 approval requirement, 12 budget. Steps 4 and 6 to 9 are still empty placeholders. Denied calls never spend budget (checked in a test).
- Step 11 stand-in: until the approval queue exists (Phase 6), a call that needs approval (POLICY_APPROVAL, GRANT_APPROVAL) is held back with `action=require_approval`. `GRANT_APPROVAL` for `approval_required_for` is implemented now because the field is accepted at grant creation and ignoring it would be a silent hole. The agent sees the generic "Blocked by firewall" text for these.
- `tools/list` filtering (F03): enforce mode returns only tools in the grant and in the registry; no valid active grant, suspended grant or any internal error returns an empty list. Monitor mode returns the whole catalog.
- Startup (F05): the gateway refuses to start, naming the tools, when an upstream provides a tool missing from tools.yaml, and it cleans up its upstream processes and database on refusal. Unreviewed tools get private+untrusted+sink and a startup warning (also stored as a `system` audit row).
- Eval harness: scenario grants now go through the registry check. `grant.expired: true` (harness only) builds an already expired grant. The shadow-tool variant registers `fs_read_flle` as an unreviewed tool, because a real operator would also have had to list it for the gateway to start.
- Admin API: header `X-Admin-Token`, constant-time compare, 5 failures in 60 s lock the API for 60 s (HTTP 429, `ADMIN_LOCKOUT`, lockout is global because all clients are on 127.0.0.1). Every route needs the token, including /health. Implemented now: /health, /grants (POST, GET, GET one, DELETE), /grants/{id}/resume, /approvals (GET, decision), /policy/test, /audit. Approval decisions are atomic (second decision 409; expired 409) and delete the stored pending arguments. The queue itself (creating rows, encryption, waiting) is Phase 6.
- Gateway and admin are separate processes sharing one SQLite file (WAL, `busy_timeout=5000`). The asyncio lock only serializes inside one process. Cross-process safe today: budget (single conditional UPDATE), grants, approvals decision (one transaction). **Phase 6 note:** the audit hash chain must use `BEGIN IMMEDIATE` so two processes cannot both append with the same previous hash.
- `fw` console script: `[project.scripts]` plus a hatchling build backend (editable install via `uv sync`). Config load errors now name file, key and a fix hint; `config_version()` feeds /health.
- Tests changed because behavior changed (not weakened): Phase 2 integration tests used placeholder grants (`allowed_tools: ["x"]`) that Phase 3 correctly denies; they now grant the tools they use.

## Phase 4 design decisions
- Pipeline is now complete up to step 12 except step 4 (pins, Phase 5) and the real approval queue (step 11 stand-in, Phase 6). Order: 1 grant, 2 suspended, 3 unknown tool, 5 scope, 6 rate/loop, 7 size, 8 secrets then paths/commands then destinations, 9 egress flow then trifecta, 10 policy, 11 approval, 12 budget. Step 14 (results): size cap, then labels, then fingerprints, then audit.
- **F09:** no pattern starts with `\b` or a lookbehind, because that disables CPython's literal-prefix search and made 1 MB scans take 250 to 400 ms. Boundaries are checked in code. JWTs and bearer tokens are tokenized first. Emails are found by scanning outward from each `@` (capped at 1000 per string). PII numbers are found by cutting out number-like runs and only classifying runs of at most 64 characters. All 20 hostile 1 MB inputs finish under 200 ms (test per input). Unicode is NFKC-normalized first.
- **F09 ambiguity (needs a decision from the owner):** the guide says PII in a sink call needs approval "unless the destination is in the grant". F11 already hard-denies any destination not in the grant, so by the time the PII check matters the destination is always in the grant. Taken literally, `PII_IN_ARGS` can never fire for a tool with a `dest_arg`. I implemented it literally: PII is detected and recorded (masked) in the audit detail of the allow verdict, no approval is added, and benign scenario BN08 ("email with PII to an allowed destination, auto_approve") therefore passes without needing approval. The alternative reading, "PII in a sink call always needs approval", is a two-line change in `engine.py` step 8.
- The recipient (`dest_arg` value) is not counted as PII in the message.
- **F10:** a path must be inside one of the tool's `path_roots` AND one of the grant's `allowed_paths` (intersection, my reading of "an allowed root that is also inside the grant allowed_paths"). Relative paths and roots resolve against `path_base` (`FW_PATH_BASE`, or the harness world dir); it must be the directory the upstream treats as its working directory. `~` and `$` anywhere in a path are rejected. Percent-encoded traversal is decoded up to twice. Symlinks and NTFS junctions are checked (the test creates a junction when symlinks are not permitted). Commands: metacharacters `; | & ` < > \n \r`, `$` of any kind, and anything not in the tool's `commands` allowlist.
- **F11:** IP literals in any notation (dotted, decimal, hex, octal, IPv6), localhost and `*.localhost` are denied unless the exact literal is in the grant. A `*.example.com` entry does not match `example.com`. Multiple email recipients must all be allowed. Only http and https URLs are accepted.
- **F12:** exact tokens are stored as hashes with a rolling-hash key and verified with a second hash, so no raw private text is at rest (test checks the tables). Fingerprints are 12-character shingles, BLAKE2b 8 bytes, winnowing window 4, overlap threshold 3, cap 50,000 per grant. Decoders: percent, base64 (standard and urlsafe, padding repaired, four alignments so a glued-on prefix does not break it), hex (two alignments), reversal, ROT13, two layers, 1 MB total, at most 64 candidates. All blobs of one kind are decoded and joined into ONE candidate so padding with junk blobs cannot push the real one out; decodings are accepted only if they are valid UTF-8 without control characters.
- **Egress buffer:** the guide says "last 4 KB of flow-normal sink-bound text". My first version failed its own chunking test (chunks shorter than 8 characters were dropped and unrelated arguments broke adjacency). It is now a list of (argument key, normal text) entries, 4 KB in total, so pieces of one secret sent through the same field are rejoined even when other fields change, and a new piece is also tried next to the 32 most recent entries of other fields (for exact tokens). The table column `text` holds this as JSON. Reversed and ROT13 variants are checked on the current call only, not buffered.
- **F13:** trifecta fires when the grant has seen both private and untrusted data (or is suspicious) and the tool is a sink. Hard denies (EXFIL_FLOW, SECRET_IN_ARGS, DEST_NOT_ALLOWED) come first. `trifecta_mode: block` returns `POLICY_DENY` with rule id `trifecta` (the guide's reason catalog has no separate code). Because `web_fetch` is both untrusted and a sink, its first call is checked before the page can taint the grant; the second call is held.
- **F08 (Tier 2, done):** defaults `rate_limit_per_min 30`, `rate_burst 10`, `loop_threshold 3`, `loop_window_s 60`, `suspend_after_denies 5` in `policy.yaml` defaults. State is per grant in `grant_state`, updated atomically. Denied attempts count toward the loop key. The circuit breaker counts consecutive hard denies on a valid grant (not NO_GRANT, expired, revoked, exhausted, too many sessions, suspended, or approval requirements), only in enforce mode; an allowed call resets the streak; the alert is a `system` audit row until F22. Existing tests that repeat calls use a relaxed policy (`relaxed_policy()` in `tests/integration/conftest.py`).
- **F33 results:** a result over 256 KB is cut and a marker appended; the structured copy keeps its shape and is trimmed too (dropping it made MCP clients reject the response, found by a test). Decision on upstream errors: the proxy returns a failing upstream tool as a normal result, so its error text is treated like any result of that tool (and is private data if the tool is private).
- **Eval changes:** E04 text was a near-verbatim copy of the note, which the flow engine (correctly) blocks before the trifecta rule is reached. It now uses a true paraphrase so that only the trifecta rule can stop it. C01 to C04 are currently stopped by the destination allowlist / secret check / tool filter, not by pinning: they do not yet isolate F04 (Phase 5).
- Process note: during this phase I made a mistake in a scripted edit that deleted several functions from `flow.py`; the test suite caught it immediately and the functions were restored.

## Phase 5 design decisions
- **F14 scanner (`scan_output.py`)**: eight families with the guide's weights (override 0.9, fake role 0.7, addressed to agent 0.6, exfil verb with target 0.7, tool call request 0.5, markdown/HTML image or link with query data 0.7, hide from user 0.8, hidden characters 0.4), combined with noisy-or. Preprocessing is NFKC, strip invisible characters, decode Unicode tag characters (they spell hidden ASCII), fold Cyrillic/Greek lookalikes, extract HTML comments and hidden elements, decode base64 blobs one level. Quarantine threshold 0.8, flag 0.4, both from `policy.yaml`.
- **Scanner speed**: the first version used patterns that are bounded but were applied at every position, which took 14 s on a megabyte of `<!--`. It now finds a cheap literal anchor first and matches a short window behind it (find loops for comments and image links, bisect over precomputed destination positions for the exfil family, substring pre-checks per family). A megabyte of hostile text takes about 0.1 to 0.2 s, because the scanner reads at most 256 KB per text (the same as the result cap; results never reach it larger). Timing tests take the best of three runs.
- **Tuning on the dev corpora** (`eval/fixtures/injection/`, 33 injection samples, 38 benign pages): all 33 are flagged or quarantined, 18 quarantined; benign pages: 1 quarantined (an article quoting "ignore previous instructions", marked `known_fp`) and 1 flagged (an instruction to "send an email to bugs@..."), i.e. 2.6% and 2.6% (`eval/results/injection_scan_report.md`, `uv run python -m eval.scan_report`). These corpora were used for tuning, so the numbers are optimistic; the held-out set in Phase 7 is the honest measurement. Rules added from false positives: `email us at ...` is contact info, `email address/account` is a noun, negated advice (`never send your password`) is ignored, windows stop at the end of the sentence, tool-call requests need an identifier with an underscore, a line starting `System:` counts only if the rest of the line contains an instruction word, joiners count only inside ASCII words.
- **Result handling order (step 14)**: size cap, binary check, injection scan, labels, fingerprints (original text), redaction, audit. A quarantined result is replaced by the guide's message (`[Firewall] Content from <tool> withheld: possible prompt injection. code=INJECTION_QUARANTINE event=<id>`); it keeps the **shape** of structured content (string leaves replaced), because MCP clients validate results against the tool's output schema and rejected the first version. The grant is flagged suspicious and gets the untrusted label. A quarantined result is not fingerprinted (the agent never saw it). The audit row carries the score, families and a snippet of at most 2 KB with secrets masked. Several text blocks of one result are scored together, so an instruction split across blocks still combines.
- **Consequence worth knowing**: after one quarantine or flag the grant is suspicious, and `web_fetch` is itself a sink, so the next fetch on that grant needs approval (`TRIFECTA_APPROVAL`). That is F13 working as written; it means one grant per task should not keep browsing after an injection was seen.
- **Monitor mode** records what the scanner would have done (`flag` row with `would_quarantine`, or `would_deny` for binary) and never changes what the agent receives. In monitor mode the detection scenarios that expect `quarantined` therefore score 1/4 (only the `flagged` one is detected); that is intended.
- **F04 pinning (`pinning.py`)**: SHA-256 over canonical JSON of name, description and input schema (output schema and annotations are not covered). Pins are written at gateway startup (first sight) and compared on every `tools/list`. States: pinned, changed, quarantined, approved_change. A changed tool stays blocked even if the upstream changes back, until an operator approves it (`POST /pins/{upstream}/{tool}/approve`, `fw pins approve`), which adopts the observed definition. When a changed definition is also flagged as poisoned the state is `changed` (code `TOOL_PINNED_CHANGED`, as in the guide's Trace 4) and the reasons are kept for the operator. Pins persist in the database, so a rug-pull between two gateway runs is caught. Step 4 of the pipeline reads the stored state on every call.
- **Poisoning scan**: angle-bracket tags such as `<IMPORTANT>`, instruction patterns reused from the output scanner, instructions to read or pass files, keys or credentials, instructions to call another tool, invisible characters or 20+ whitespace characters, parameters named like hidden channels (`notes`, `context`, `extra`, ...) that neither the schema nor the description explains, a name within edit distance 2 of a reserved name (`read_file`, `send_email`, `execute`, `shell`; the unprefixed name is compared and exact matches are fine) and, if it is not reviewed, within edit distance 2 of another registered tool. The reviewed `fs_read_file` is never flagged because of its unreviewed look-alike. The demo tools' real descriptions are not flagged (test).
- **Not covered by pinning**: a server that changes behavior without changing its listing, and changes between listings if the agent does not re-list (calls use the stored pin state). Listing is the only moment definitions are observed.
- **Rug-pull demo server**: `context` is only advertised in `schema` mode from the second listing; before this fix the benign mode already advertised it and was (correctly) quarantined at first sight.
- **Eval**: C01 to C04 are now stopped by the tool filter and pins before the agent can call anything (the earlier blocks were incidental). New detection scenarios F01 to F04 with community pages on the allowed host (`docs.example.com/community/...`), reported as detection rates. Gateway enforce run: attacks 0/20, detection 4/4, controls 4/4, benign 8/8.
- **F15 redaction**: `policy.redact_private_secrets` masks detected secrets in results of private tools with `[REDACTED:<kind>#<hash>]` (stable per value), in text blocks, embedded text resources and structured content; fingerprints come from the original text, so sending the real value is still caught (test).
- **F40 (partly)**: structured content and embedded text resources are scanned and fingerprinted; image, audio and embedded binary blocks from an untrusted tool are replaced by `BINARY_BLOCKED` unless `block_binary_from_untrusted` is false. **Not done:** scenario H6 (injection in structured and embedded-resource content through a real upstream): the demo servers return plain text only. It is covered by unit tests on synthetic results.
- **F39**: the proxy relayed server-initiated sampling and elicitation to the agent by default (a control test proves it). `ProxyClient` is now built with refusing handlers: sampling raises, elicitation declines, roots are empty, and each attempt writes an audit row `UPSTREAM_REQUEST_BLOCKED`. Scenario H5 is covered by an integration test with a test-only upstream, not by the eval runner.
- Known limitation: the earlier `tools.yaml` rule still holds, an upstream that provides a tool missing from `tools.yaml` stops the gateway from starting.
